## Code and configuration findings

### F1 — Pending integration prevents claiming completion of 1585 and 1586

**Priority: high for workshop completion.** PR #9 and PR #10 are both open, each currently showing zero GitHub checks. `main` still creates implementation commits titled `Issue #N automatisch umsetzen` and PRs titled `Issue #N: ...` ([publisher](.github/scripts/issue-implementation.cjs), lines 216–232), without the requested reviewer checklist. PR #9 addresses this. The PR-review workflow exists only in PR #10. Merging either PR requires explicit user authorization; this audit did not merge them.

### F2 — No live implementation or PR-review acceptance evidence

**Priority: high for confidence in automation.** Helper tests mock GitHub and validate important boundaries, but cannot establish runner permissions, network behavior, agent output, real publication, or cross-workflow handoff. Setup and issue-clarification analysis have real successful runs. Implementation has no runs; PR review has not been integrated. Therefore the complete analysis → Red/Green/Blue/finalisation → verified PR → review chain is unverified. Preserve the distinction even after the pending PRs are merged.

### F3 — Application unit-test infrastructure remains broken

**Priority: medium; blocking when a requirement needs unit tests.** [package.json](package.json) does not declare the Karma/Jasmine packages required by the configured unit runner. There are no application unit `*.spec.ts` files under `src/`. Today's `ng test --watch=false` fails with `Cannot find module 'karma-jasmine'` before executing assertions.

The Red/Green skills and implementation prompt correctly report this limitation instead of treating it as a valid behavioral failure or silently repairing infrastructure. The independent implementation verifier runs builds and Playwright tests; it does not provide a working application unit gate. This does not invalidate the skill-creation tasks, but it prevents a claim that arbitrary unit-test-based feature delivery is ready. A runner migration or repair is a separate task requiring approval.

### F4 — Readiness and implementation-authorization language conflict

**Priority: medium; clarify the automation contract.** The [analysis prompt](.github/codex/prompts/issue-analysis.md), final paragraph, explicitly says its label is not authorization to implement. The [orchestration skill](.agents/skills/j-feature-delivery/SKILL.md) also distinguishes analysis suggestions from permission. However, [issue-analysis.cjs](.github/scripts/issue-analysis.cjs), lines 138–157, automatically dispatches implementation after a ready result, and the [implementation prompt](.github/codex/prompts/issue-implementation.md) assumes maintainer authorization.

This is not evidence of an unauthorized action in this session: automatic implementation was previously requested, and collaborator/fingerprint gates exist. It is a maintenance risk for future users who may expect “analyze” to stop at analysis. State clearly whether trusted issue submission/reanalysis grants bounded implementation permission, or introduce an explicit approval gate in a separately authorized change. Do not let a model's quality label ambiguously define business approval.

### F5 — No enforced merge gate or general PR validation workflow

**Priority: medium for repository operation; additional hardening, not a missing workshop requirement.** GitHub shows no rulesets and no classic branch protection. `main` has no general PR build/test workflow; independent verification exists inside the automated implementation path only. Therefore a normal human PR can be merged without successful build/tests or review. The future Codex review is a comment, not an approving human review or an enforced quality gate.

If enforcement is desired, first add a deterministic PR validation workflow, establish successful checks, and then require those checks through a `main` ruleset. Consider review requirements appropriate for a solo-maintainer repository; requiring another human approval can block a sole author's work. This is ordinary CI hardening, separate from the inactive Self-Healing CI exercise. No deployment pipeline is required by the inspected active tasks.

### F6 — Known list search race and lifecycle risks remain

**Priority: medium for application maintenance; not a new failure of the completed scoped refactoring.** [book-list.component.ts](src/app/books/book-list.component.ts), lines 19–51, uses an `any` timer, separate HTTP subscriptions, and no teardown. Out-of-order responses can replace newer search results; clearing search does not cancel the pending debounce timer; navigation does not explicitly dispose the timer. Errors are logged without a dedicated visible error state. These are source-confirmed risks; a failing race test was not added during this review. The current regressions pass and do not prove these races absent. `ARCHITECTURE.md` already records the deferred scope. The detail component uses a stronger route-stream/switchMap approach.

### F7 — Runner/action maintenance and formatting need follow-up

**Priority: low.** Successful GitHub runs carry warnings about Node 20 action runtimes (`checkout@v4` / `github-script@v7`) being forced onto Node 24, and notices about `ubuntu-latest` migrating to Ubuntu 26. The trainer's Ubuntu 24.04 suggestion is therefore relevant to reproducibility, but the observed runs succeeded; these notices are not current failures. Action tags and the installed Codex CLI are not fully version-pinned, so future upstream changes can affect reproducibility.

The current standard Prettier check reports six files: three implementation workflow/helper files due to line endings, plus `context-recovery`, `j-feature-delivery`, and `requirements-finalisation` Markdown formatting. Repeating with `--end-of-line auto` leaves only those three Markdown warnings. These are formatting findings, not behavioral failures. Nothing was reformatted during the audit.

### F8 — Personal-instruction wording differs from the integrated repository policy

**Priority: low; clarify policy rather than creating files.** The personal instructions supplied in chat say local phase skills stay ignored. Current root `AGENTS.md`, lines 9–12, explicitly versions the five phase skills, existing context helper and orchestration skill so Actions can read them. That matches the already integrated runner architecture. Keep the distinction between shared workflow skills and other personal skills explicit to avoid later deleting runner prerequisites or accidentally publishing unrelated personal material. No additional skill is needed for any finding in this report.

## Skill dependencies and Codex adaptation

There are still exactly **five phase skills**: interviewer, Red, Green, Blue and finalisation. `context-recovery` is a helper and `j-feature-delivery` coordinates them; neither replaces a phase. No additional phase skill is required by the tasks or chat examples.
